# M5 · 定时任务（无人值守，出报告或提 PR）

> 目标：工作流不再只能手动点「运行」。到点自动唤醒，没人看着也跑完，产出**一份可看的报告**，
> 需要时把结果推到远端并开 PR；失败、超时、需要人点头时，留下痕迹等你回来处理。
>
> **状态：已实现（v0.6.0）。** 下面保留方案与取舍，供后续维护对照；实施结果见 §12。

## 0. 一个必须先说清的前提

M4 的 AI 能力没有变化，M5 改的是「**什么时候跑、没人时怎么办**」。这带来一个天然的矛盾：

- 自动运行意味着**没有人在场逐处确认**；
- 而 M1–M4 里最有价值的约束（逐处接受、审批门）恰恰依赖人在场。

所以 M5 的核心不是加一个 cron，而是定义一套**无人值守下的边界**：能花多少钱、能碰哪些文件、
没人批的审批门怎么落地、失败到什么程度自己停。这套边界是本方案最需要你拍板的部分（见 §10）。

## 1. 现状盘点（M5 的起点）

| 已有 | 位置 | M5 怎么用 |
| --- | --- | --- |
| 触发器节点带 `schedule` / `timezone` / `enabled` | `packages/core/src/workflow.ts` | 作为排期的**唯一来源**，不再另建一套计划表 |
| 工作流执行器（DAG、worktree、合并、审批门） | `apps/desktop/src/workflow-runner.ts` | 直接复用，`requestGate` 换成无人值守策略 |
| 审批门 + 超时 | 同上 | 单人无人时默认「暂停并通知」，等你回来 |
| 结果分支 `olivia/wf-<runId>` | 同上 | 报告的「产物」，也是自动 PR 的源分支 |
| 令牌保险箱（safeStorage） | `apps/desktop/src/vault.ts` | 复用同一套加密存储，扩展为「模型密钥」 |
| 事件日志 / 会话重放 | `packages/core/src/session.ts` | 运行历史的一种来源，但**不持久化运行态** |
| mock 端点 + 临时仓库自检 | `apps/desktop/src/wf-selftest.ts` | 扩展成可注入时钟的排期自检 |

**三个明确的缺口**：

1. 没有常驻调度器——主进程只在窗口活着时存在，且从不看触发器的 `schedule`。
2. 没有持久化的运行历史——`WorkflowRunState` 只在内存里，关掉应用就没了。
3. 无人值守时**没有可用的模型密钥**——API Key 只存在渲染层内存，唤醒时渲染层可能根本没开。

## 2. 范围与非目标

**做**：
- 常驻调度器（主进程），重启后按 `nextRunAt` 续跑；
- 触发器的排期变成真排期，支持预览「接下来 5 次」；
- 无人值守执行：预算上限、审批门策略、失败即停；
- 每次运行产出一份 Markdown 报告（落盘、可导出）；
- 可选：成功后推送结果分支并开 PR（按计划单独开关）；
- 界面：计划列表、下次运行、最近结果、立即运行、暂停/启用、失败原因；
- 离线自检：虚拟时钟 + mock 模型，不依赖真实时间与外部服务。

**不做（明确推到 M6+）**：
- 操作系统级计划任务（开机自启、系统 cron / Task Scheduler）——M5 只在应用运行时调度，关掉应用不跑；
- 多机分布式调度、跨设备同步；
- 日历式 / 一次性 / 手动触发之外的复杂事件源（webhook、文件监听）；
- 冲突自动解决（合并冲突仍按 M4：失败交还给人）。

## 3. 核心设计决定

### D1 排期从触发节点派生，不另建计划表

工作流画布上的「定时触发器」就是计划本身：`enabled && schedule` 的每个 trigger 节点 = 一条排期。
标识用 `workflowId + nodeId`，改名字不会丢历史。

- 理由：避免「画布上写着每晚 22:00、计划页写着别的」这类双源漂移；
- 多个触发器 = 多条排期（互相独立），不尝试把 cron 做语义合并；
- 不支持的表达式**丢弃并标红**，不做猜测。

### D2 调度器在渲染层之外

计划在**主进程**常驻，界面关掉也照跑；所有计划变更走主进程 IPC，不写 localStorage。
这样也和「能力在主进程」的既有架构一致。

### D3 账本三件套，全部落盘

| 文件 | 内容 |
| --- | --- |
| `<userData>/schedules.json` | 计划注册表 + 运行态（`lastRunAt` / `nextRunAt` / `lastResult` / `enabled`） |
| `<userData>/runs/<runId>.json` | 每次运行的持久记录（状态、节点、错误、报告路径） |
| `<userData>/reports/<scheduleId>/<runId>.md` | 人看的报告 |

运行记录先写「运行中」，结束时落终态。崩溃后下次启动把「运行中」判为 `interrupted`，
不假装成功。

### D4 无人值守的策略是「预算 + 门禁」，不是「全部放行」

每条排期带一份**独立于交互式审批**的策略：

- 预算：单次墙钟上限（默认 30 分钟）、节点数上限、token/步数上限；
- 工具白名单：默认仍是各节点上配的，排期可以再收紧，不能放宽；
- 审批门：`pause-and-notify`（默认）/ `auto-approve` / `auto-reject`；
- 任一项触发即**失败关闭**（fail closed）：终止运行、出失败报告、不推送。

### D5 模型密钥：加密落盘 + 环境变量回退

无人值守必须有凭据，但「把 Key 常驻磁盘」是新增的风险面，必须显式：

- 复用 `safeStorage`，加密存 `<userData>/credentials.bin`（与 Git 令牌同一个保险箱，新开 `model` 分区）；
- 设置页只写不读，和令牌一致；渲染层永远拿不到明文；
- 若未存，回退 `OLIVIA_BASE_URL` / `OLIVIA_API_KEY` 环境变量；
- 都没有 → 计划启动时**预检失败**并通知，不产生半次运行。

### D6 结果分支的处置：默认不推远端

- 默认：结果留在本地 `olivia/wf-<id>`，报告里给出分支名，你回来自己看/推；
- 每条排期可选「成功后推送并开 PR」；
- 开 PR 用现有 `providers.ts`（GitHub / GitCode），PR 正文由报告生成；
- 幂等：以 `runId` 做去重，重跑不会重复开 PR。

## 4. 数据模型

```ts
export type GateMode = 'pause-and-notify' | 'auto-approve' | 'auto-reject';
export type UnattendedMode = 'off' | 'report' | 'report-pr';

export interface UnattendedPolicy {
  gate: GateMode;
  /** 无人应答时，审批门最多等多久（分钟），超时按拒绝 */
  gateTimeout: number;
  /** 单次运行墙钟上限（分钟） */
  maxWallMinutes: number;
  /** 单次运行最多节点数（防误配的巨型画布） */
  maxNodes: number;
  /** 单次运行模型步数上限 */
  maxSteps: number;
}

export interface ScheduleRecord {
  /** workflowId + triggerNodeId */
  id: string;
  workflowId: string;
  triggerNodeId: string;
  workspace: string;
  cron: string;          // 标准 5 段
  timezone: string;      // IANA，例如 Asia/Shanghai
  enabled: boolean;
  mode: UnattendedMode;
  policy: UnattendedPolicy;
  /** 生命周期 */
  lastRunAt?: number;
  lastStatus?: 'done' | 'failed' | 'canceled' | 'skipped' | 'interrupted';
  nextRunAt?: number;
}

export interface RunRecord {
  id: string;
  scheduleId: string;
  workflowName: string;
  workspace: string;
  startedAt: number;
  endedAt?: number;
  status: 'running' | 'done' | 'failed' | 'canceled' | 'skipped' | 'interrupted';
  branch?: string;
  reportPath?: string;
  prUrl?: string;
  error?: string;
  nodes: Record<string, { title: string; phase: string; summary?: string; error?: string }>;
}
```

## 5. 调度算法

- 解析 5 段 cron（`*`、`*/n`、`a-b`、列表、月份/星期英文缩写），按 **IANA 时区**求下一次触发；
  用 `Intl.DateTimeFormat` 做时区换算，不引入日期库。
- 单定时器：只对「最早的下一次」设一个 timer；任何注册变更都重算。
- 唤醒后：
  1. 取进程内租约（同一 schedule 并发只允许一个）；
  2. 预检：工作区存在 / 是 git 仓库 / 有提交 / 有凭据；
  3. 落 `runs/<runId>.json` 为 `running`；
  4. 调 `runWorkflow`，把 `requestGate` 换成无人值守策略；
  5. 出报告、落终态、更新 `lastRunAt / nextRunAt`、通知界面。
- **错过补跑**：应用关机期间错过的，启动时若 `nextRunAt < now`，**只补跑最近一次**，其余记为 `skipped` 并写明原因（默认策略；也可配置成「不补跑」）。
- **重叠**：上一次还没跑完，本次默认**跳过并记一条**，不排队（排队会让晚高峰叠成雪崩）。
- **失败不重试**：M5 不做自动重试，失败报告 + 通知；重试留给人工「立即运行」。

## 6. 运行流程（无人值守）

```
调度触发
  └─ 预检 ──失败──> 记 failed + 通知（不出报告）
  └─ 通过 ──> runWorkflow（同 M4）
                ├─ 预算超限 ──> 终止 + 失败报告
                ├─ 审批门 ──策略──> auto-approve / auto-reject / 等 TTL
                ├─ 合并冲突 ──> 失败（保留集成分支现状）
                └─ 成功 ──> 报告 ──mode=report-pr?──> 推送 + 开 PR
```

报告模板（固定结构，便于机器解析与人工扫读）：

```md
# <工作流名> · <时间>
- 结果：成功 / 失败（原因）
- 结果分支：olivia/wf-xxxx（未推送）
- 节点：拆解 ✅ / 接口层 ✅ / 页面层 ✅ / 评审 ⚠ 2 条建议 / 审批门 ⏸ 超时拒绝
- 改动：3 个文件，+120 −34
- 评审结论：…
- 风险与建议：…
- 日志尾部：…
```

## 7. 界面

侧栏新增「计划」（任务 / 工作流 / 计划 / Git / 设置）：

- **列表**：计划名（=触发器标题）、所属工作流、`每晚 22:00（Asia/Shanghai）`、下次运行、上次结果
  （成功/失败/跳过 + 耗时）、启用开关、立即运行。
- **详情**：接下来 5 次运行时间预览；无人值守策略（预算 / 门禁模式）；最近 10 次运行与报告链接；
  「最近一次失败」的原始错误。
- **首次启用确认**（不可省）：明确写出「它会在你不看着的时候改这个工作区的文件、
  可能推送分支并开 PR、失败会停下来等你」，确认后才写入 `enabled: true`。
- **运行中**：复用 M4 的运行面板；无人值守模式额外显示「NS · 无人值守」标记，避免和手动运行混淆。

## 8. 测试计划（全部离线）

- **虚拟时钟**：调度器的 `now()` 可注入，自检里直接把时间推快，不 sleep 真实时间。
- 调度单测：cron 解析（含非法表达式）、时区换算、DST 前后、`nextRunAt` 单调不重复。
- 调度器自检（扩展 `wf-selftest.ts`）：
  - 到点触发一次，且只触发一次；
  - 关机错过 3 次 → 只补跑最近一次，另 2 次 `skipped`；
  - 上次未完成 → 本次跳过并记录；
  - `pause-and-notify` → 停在门；TTL 过期 → 失败；
  - 预算超限 → 失败关闭，不出 PR；
  - 报告文件生成且可被解析；
  - 一条计划失败不影响其他计划。
- e2e：真实 Electron 里注入一条「1 分钟后」的计划 + mock 模型，等它自己跑完、报告落盘、界面出现结果。

## 9. 风险与取舍

| 风险 | 处理 |
| --- | --- |
| 无人值守自动改代码、自动提 PR | 默认只出报告、不推远端；开 PR 需单独开关 + 首次确认 |
| Key 常驻磁盘 | safeStorage 加密、只写不读；也可只用环境变量 |
| 计划在应用关闭时「静默失效」 | 界面明确「应用运行时才会触发」；启动补跑最近一次 |
| 两个计划同时改同一个工作区 | worktree 天然隔离；但同工作区并发跑默认禁止（租约 + 跳过） |
| 巨型画布烧钱 | 节点数 / 步数 / 墙钟三重预算，超限失败关闭 |
| DST 导致某天多跑/少跑 | 用 IANA 时区 + `Intl` 计算；自检覆盖切换日 |

## 11. 实施顺序（实际按此落地）

1. 契约：`packages/core/src/schedule.ts`（cron 解析 / nextOccurrence / 排期与运行类型）。
2. 持久层：`scheduler-store.ts`（原子写、损坏容错、崩溃标记 interrupted）。
3. 同步：`schedule-sync.ts`（画布触发器 → 账本，保留用户手动启停）。

5. 报告：`report.ts`（固定 Markdown 结构）。

7. 凭据：`vault.ts` + 设置页「无人值守凭据」。
8. 自检：`scheduler-selftest.ts`（27 条，虚拟时钟）。

## 12. 实施结果（与方案一致的地方与不一致的地方）

一致：排期派生、常驻 tick、只补最近一次、重叠跳过、三重预算、三档门禁、失败关闭、
报告落盘、可选 PR、首次启用确认、离线自检。

实现时敲定的细节：

- **新计划默认暂停**：画布上填了 cron 只是「候选计划」，必须到「计划」页确认启用后才开始定时运行——避免填个表达式就悄悄开始无人值守改代码。启停状态由调度器账本持有，画布再保存不会覆盖。
- **重启补跑的实现要点**：启动时 `recompute()` 优先沿用账本里那个**已经过期**的 `nextRunAt`（那正是关机期间错过的那次），交给 tick 去补跑；只有刚创建、还没有下次时间的才从当前时间往后算。
- **墙钟预算**是整轮 abort（模型流、命令、审批门都会收到取消信号）；**步数预算**按工具调用计数。两者都算「预算失败」，不是「用户取消」。
- **门等待**：`pause-and-notify` 在无人值守下就是「等到 TTL 再判未通过」，并在此之前发一条系统通知。
- **PR 推送**用 `git push origin <branch>:refs/heads/<branch>`（集成结果分支不在当前工作区里，不能靠 `push HEAD`）；PR 正文取报告前 8KB。
- **报告目录**：`<userData>/reports/<scheduleId>/<runId>.md`；界面只能打开这个目录内的文件。

## 13. 怎么用

1. 工作流画布上给「定时触发器」填 cron 与时间区（默认 `0 22 * * *` / `Asia/Shanghai`）。
2. 到「设置 → 无人值守凭据」保存模型 Base URL 与 Key（只写不读；不存则回退环境变量）。
3. 给当前任务绑定一个 git 仓库（工作区）。
4. 打开「计划」页：列表里会出现这条计划，点开关启用，第一次会弹确认。
5. 想马上验证：点「立即运行」，完成后在「运行历史」点「报告」。

## 14. 已知限制

- 只在应用运行时调度；关机不跑，重启只补最近一次。
- 不做自动重试；失败靠报告的「错误与告警」+ 历史定位。
- 同工作区同一时刻只跑一个计划（其他计划重叠时跳过，不排队）。
- 审批门「暂停并通知」在无人值守下等价于「等 TTL 后失败」——这是刻意选择：宁可停下，也不替你点头。
- 报告是 Markdown 文件，没有内嵌 diff 渲染；看具体改动仍用 Git 页或结果分支。
