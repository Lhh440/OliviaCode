# M4 · 多智能体并行与工作流真实执行

> 画布上的「运行工作流」不再只是按顺序点亮节点：主进程按 DAG 调度，真正把每个 Agent 节点派发出去，
> 各自在独立的 git worktree 里改代码，跑完合并成一条结果分支，审批门停下来等人。

## 一条工作流是怎么跑的

```
trigger ──┬─> agent A ──┐
          └─> agent B ──┴─> gate（等人） ──> output（汇总分支/文件/提交）
```

1. **准备**：要求绑定的是 git 仓库且至少有一次提交。主进程从 `HEAD` 开一个集成分支
   `olivia/wf-<runId>`，对应一个临时 worktree（放在应用数据目录，不碰用户的工作区）。
2. **调度**：节点的所有上游都 `done` 才启动；agent / reviewer 受并发上限约束（默认 3，最多 6）。
   上游失败或跳过，下游直接 `skipped`。
3. **隔离**：每个 agent 节点从 `HEAD` 再开一个独立 worktree 与分支 `olivia/wf-<runId>-<nodeId>`，
   `Policy.root` 指向这个 worktree —— 读写、命令、git 全在里头，两个 worker 同时改同名文件也不会互相踩。
4. **合并**：节点跑完把 worktree 里的改动提交（`wf: <节点名>`），再串行合并进集成分支
   （`--no-ff`，保留每个 worker 的提交）。合并成功后拆掉 worktree、删掉 worker 分支。
5. **评审**：reviewer 节点在集成分支的 worktree 上以**只读**模式运行，只给 `read` / `git` 工具，
   上下文干净，先看 `git diff --stat` 再下结论。
6. **审批门**：gate 节点把状态切成 `waiting`，主进程把 `gate.waiting` 事件发给界面，等「批准并继续 / 停止」。
   等待期间不占用并发额度；30 分钟没人理按拒绝处理。
7. **产出**：output 节点统计结果分支的提交数、改动文件与 diffstat，写进运行日志与节点摘要。
   结果分支留在仓库里，用户可以在 Git 页检查、切过去、或开 PR。
8. **收尾**：无论成功失败，集成分支的 worktree 与所有 worker worktree 都会拆掉；
   `git worktree list` 回到只剩主工作区。

## 界面

- 画布节点实时跟着状态变色：运行中 / 等待你 / 完成 / 失败 / 未配置。
- 左下角运行面板：整体阶段、每个节点的状态点、最近日志（工具调用、写入、合并、错误）、结果分支。
- 审批门出现时面板就地展开「批准并继续 / 停止」，右上角的主按钮同步变成「批准并继续」。
- 运行中可以「取消」：中断模型流、拒绝未决的审批门、拆掉临时 worktree。

## 已知限制

- **只在 git 仓库里跑**：隔离依赖 worktree；非 git 目录直接拒绝，不会退化成「共享工作区硬跑」。
- **合并冲突会让运行失败**：worker 分支合并进集成分支时不做冲突解决 UI，报错并保留集成分支现状，交给人处理。
- **重试上限 2 次**：节点配置里的 `retries` 目前只放行一次重跑（worktree 会先 reset 到 HEAD）。
- **结果分支不自动推送**：push / PR 仍走 Git 页或对话里的工具，避免工作流在无人值守时改远端。
- **reviewer 看的是集成分支现状**，不会逐行评论；结论是文本，落在节点摘要与日志里。
- 每个运行会在应用数据目录留一份 worktree 元数据，收尾时删除；异常退出可能残留，`git worktree prune` 可清。
